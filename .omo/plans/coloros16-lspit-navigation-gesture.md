# coloros16-lspit-navigation-gesture - Work Plan
## TL;DR (For humans)
**What this drives:** Creates a conditional, discovery-first implementation path for an Android 16 / ColorOS 16 hook module that disables only touchscreen left/right edge-swipe Back recognition while preserving bottom-up Home/Recents gestures for third-party gesture software.

**Why this approach:** AOSP separates SystemUI `edge-swipe` Back handling from launcher/Quickstep `swipe-up` handling, but ColorOS 16 class names, obfuscation, host packaging, and API support are unverified. The worker must prove the exact LSP-IT host contract and target-firmware hook point before enabling any hook.

**What it will NOT do:** It will not change global navigation mode, hook Launcher/Quickstep, intercept global `InputDispatcher`/`pilferPointers`, suppress all Back sources, assume LSPosed/LSPatch compatibility, or activate a broad name-based fallback when target discovery is ambiguous.

**Effort / risk:** Medium-to-high implementation effort; high runtime risk because SystemUI and vendor framework code are OEM-specific. Deployment is `NO-GO` if host identity, recovery path, target artifact match, or safe narrow hook evidence is missing.

**Decisions made:** Default scope is touchscreen left/right edge-down recognition only. Bottom Home/Recents, hardware/key Back, app callbacks, predictive Back outside the edge recognizer, stylus, trackpad, gesture-exclusion semantics, and other navigation sources remain untouched. Android platform API 36, libxposed API 102, LSP-IT host API, compileSdk, targetSdk, and minSdk remain separate compatibility fields. SDK 36 is the default compile/target baseline; SDK 37 is allowed only when host/build evidence requires it.

**Execution handoff:** A separate worker session started by the user runs this plan. It must stop at any `NO-GO` gate and preserve evidence; approval of this plan authorizes plan execution only in that worker session, not silent implementation in this planning session.

## Scope

### In scope
- Confirming the exact LSP-IT host/release, module metadata, host API, install model, Android 16 support, and reliable disable/recovery path.
- Building a modern libxposed API 102-style module only if the host contract accepts it; otherwise following the host-documented packaging branch.
- Capturing Android 16 / ColorOS 16 device identity, navigation configuration, SystemUI/framework artifacts, hashes, class-loader information, and gesture traces.
- Selecting one allowlisted SystemUI-side touchscreen Back decision point on the exact firmware.
- Suppressing only regular left/right edge touchscreen Back recognition while leaving bottom Quickstep/Home/Recents paths intact.
- Adding fail-closed runtime checks, diagnostic logging, a kill-switch, rollback procedure, and machine-readable evidence.

### Must NOT have
- No implementation before host and device gates pass.
- No assumption that “LSP-IT” means LSPosed or LSPatch.
- No use of AOSP class names as proof of ColorOS implementation.
- No global navigation-mode change.
- No hooks in Launcher/Quickstep `TouchInteractionService`, `OrientationTouchTransformer`, `OtherActivityInputConsumer`, `OverviewInputConsumer`, `AbsSwipeUpHandler`, or the launcher `swipe-up` monitor.
- No global `InputMonitorCompat.pilferPointers()`, `InputDispatcher`, `BackNavigationController`, final `KEYCODE_BACK`, or all `OnBackInvoked` callbacks.
- No broad class-name scan fallback, descriptor-agnostic hook, or activation on unknown SystemUI APK hash.
- No requirement for root, Magisk, Zygisk, unlocked bootloader, SDK 37, or Java 21 unless host/build evidence proves it necessary.
- No promise of ColorOS OTA compatibility beyond recorded firmware identity and verified artifact hash.

## Verification strategy
- Every task writes evidence to `.omo/evidence/coloros16-lspit/<run-id>/` with stable filenames; no acceptance criterion relies on “looks right” or worker self-report.
- Host contract gate: exact repository/release or APK identity, host API, module format, scope rules, install path, disable path, and Android 16 support are recorded. Missing identity or undocumented recovery yields `NO-GO`.
- Device gate: exactly one authorized ADB device, SDK 36, recorded build fingerprint/ColorOS version/navigation mode, successful artifact extraction, and recovery access.
- Discovery gate: exact APK hash, class loader, declaring class, method descriptor, and dynamic side-Back evidence are recorded. Any missing, ambiguous, mismatched, or coupled result yields `NO_MATCH`, `UNSAFE_COUPLING`, or `NO_GO` and prevents activation.
- Build gate: only after host/device gates; `gradlew.bat test` and `gradlew.bat assembleRelease` must pass, and APK metadata is inspected.
- Behavior gate: left and right side swipes stop triggering Back; bottom Home and Recents continue; key Back remains unchanged; SystemUI remains stable; failure and rollback paths are verified.
- Evidence set: `host-contract.json`, `preflight.json`, `systemui.sha256`, `discovery.json`, `build.txt`, `logcat.txt`, `getevent.txt`, `gesture-results.json`, `rollback.txt`, and `research-sources.json`.

## Execution strategy
- Wave 1: Tasks 1 and 2 run independently. Task 1 locks host packaging and recovery; Task 2 validates the device/ADB branch.
- Wave 2: Task 3 performs bounded SystemUI/framework/launcher discovery after Task 2; it may end in `MATCH`, `NO_MATCH`, `UNSAFE_COUPLING`, or `NO_GO`.
- Wave 3: Task 4 creates the module baseline only after Task 1 and a safe Task 3 result. Task 5 implements policy and runtime hook only after Tasks 1, 3, and 4.
- Wave 4: Tasks 6 and 7 package/recover and run device behavior validation after Task 5.
- Wave 5: Task 8 records compatibility/documentation and release evidence after all prior tasks.
- Stop conditions are mandatory: unknown host, unsupported API, missing recovery, inaccessible artifacts, ambiguous target, unsafe coupling, build failure, SystemUI instability, or failed bottom-gesture preservation.
